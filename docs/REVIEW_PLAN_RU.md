# Независимая проверка Client Control только средствами GitHub

## Назначение

Этот процесс рассчитан на проверяющего, у которого есть только браузер и учётная запись GitHub. Локальный клон, терминал, SSH-доступ к компьютеру автора, TING/OPNsense, тестовые пароли и API-ключи не требуются.

Проверяющий использует:

- страницу commit или pull request;
- вкладки **Files changed**, **Checks** и **Actions**;
- просмотр исходников и истории через веб-интерфейс GitHub;
- GitHub Issues для замечаний и оценки новых функций.

Цель — независимо проверить опубликованные исходники, автоматические тесты, документацию и обоснованность заявлений. Автор не должен подменять результат объяснениями вне GitHub.

## Граница доказательств

Зелёный GitHub Actions check не доказывает работу сетевого шлюза. Он подтверждает только то, что фактически выполнялось на GitHub-hosted runner.

| GitHub может подтвердить | GitHub без реального шлюза не может подтвердить |
|---|---|
| синтаксис PHP, Python, shell и XML | установку пакета на TING/OPNsense |
| детерминированные тесты Compiler, Planner и ScheduleEvaluator | совместимость с фактическими API конкретной версии OPNsense |
| правила владения, конфликта и идемпотентности на тестовых данных | загрузку firewall, IPFW и Traffic Shaper |
| полноту русского каталога и совпадение сгенерированных файлов | реальное отображение и работу страницы в браузере OPNsense |
| отсутствие build-артефактов среди tracked-файлов | разрешение и блокировку настоящего трафика |
| содержание сценариев установки, отката и удаления | фактическую скорость download/upload |
| изменения между commit и pull request | ARP/NDP, расписания, перезагрузку и откат на шлюзе |

Непроверяемые через GitHub пункты получают статус **«не проверено: требуется runtime-стенд»**. Их нельзя отмечать как успешные по анализу кода, скриншоту автора или зелёному CI.

## Условия независимости

1. Проверяющий не является автором проверяемого commit или pull request.
2. Проверяется точный SHA, указанный в отчёте.
3. Вся доказательная база — публичные GitHub-ссылки: permalink на строки, diff, run и job log, issue или review comment.
4. Личные сообщения и устные пояснения автора не считаются доказательством.
5. Сначала изучается workflow, затем его результат: изменённый самим автором тест может давать ложный зелёный статус.
6. Замечание описывает конкретный риск, воспроизводимый путь в GitHub и ожидаемое исправление.
7. Runtime-свойства всегда отделяются от свойств исходного кода.

## Встроенная автоматическая проверка

Workflow [GitHub-only review](https://github.com/Omnividente/opnsense-client-control/actions/workflows/github-review.yml) запускается для `push` в `main`, для pull request и вручную.

Он использует только GitHub-hosted `ubuntu-24.04` runner и выполняет:

1. checkout точной ревизии;
2. проверку наличия PHP `gettext` и `SimpleXML`, а также русской UTF-8 locale;
3. `php -l` для всех PHP-файлов;
4. `xmllint` для XML-моделей и форм;
5. `shellcheck` для install/build/deploy/GC-сценариев;
6. компиляцию Python API smoke-теста без его запуска;
7. повторную компиляцию gettext-каталога;
8. `tests/run.php` для Compiler, Planner, ScheduleEvaluator, контроллерных соглашений, переводов и защитных инвариантов;
9. `git diff --exit-code` для сгенерированных переводов и контрольных сумм;
10. отказ, если `.pkg`, `.txz`, `.build` или `dist` попали в tracked-файлы.

Workflow не получает secrets, использует `GITHUB_TOKEN` только с правом `contents: read`, не применяет `pull_request_target` и не запускается на self-hosted runner. Единственный action закреплён на полном commit SHA.

## Порядок проверки в веб-интерфейсе GitHub

### 1. Зафиксировать объект проверки

Откройте pull request или commit и запишите:

- полный SHA;
- автора;
- дату;
- ссылку на diff;
- ссылку на соответствующий Actions run.

Для pull request проверяйте текущий head SHA после последнего изменения. Старый зелёный run для предыдущего SHA не подходит.

### 2. Проверить сам workflow

Откройте `.github/workflows/github-review.yml` в проверяемой ревизии и убедитесь, что:

- событие pull request — `pull_request`, а не `pull_request_target`;
- runner — GitHub-hosted;
- permissions ограничены `contents: read`;
- workflow не читает secrets;
- checkout закреплён на полном SHA и не сохраняет credentials;
- команды берутся из той же проверяемой ревизии;
- ошибки не скрыты через `continue-on-error`, `|| true` или безусловный успешный exit;
- runtime-ограничения явно присутствуют в Job Summary.

Если workflow небезопасен или может пропустить ошибку, весь его зелёный результат считается недостоверным.

### 3. Проверить Actions run

На вкладке **Checks** или **Actions**:

1. сопоставьте reviewed SHA и SHA запуска;
2. откройте каждый step, а не только общий зелёный значок;
3. убедитесь, что `Repository checks` действительно выполнялся и не был skipped;
4. зафиксируйте число assertions из `tests/run.php`;
5. проверьте Job Summary и список явно непроверенных runtime-свойств;
6. приложите permalink на run к итоговому issue.

### 4. Проверить состав публикации

Через **Code** и **History** проверьте:

- нет ли `.build`, `dist`, `.pkg`, `.txz`, дампов, логов или резервных копий;
- нет ли паролей, токенов, private keys, реальных API endpoints и локальных адресов;
- совпадают ли `PLUGIN_VERSION`, `PLUGIN_WWW`, README и инструкция;
- присутствуют ли LICENSE, исходный PO-каталог и его контрольные суммы;
- не скрывает ли один commit несвязанные крупные изменения;
- объяснены ли изменения, влияющие на доступ, удаление объектов или откат.

GitHub Secret scanning полезен как дополнительный сигнал, но его отсутствие не заменяет просмотр diff и истории.

### 5. Проверить защитные инварианты кода

Для каждого пункта нужен permalink на реализацию и permalink на тест либо отдельное замечание об отсутствии теста.

Проверить:

1. новая установка выключена и не применяет правила автоматически;
2. сохранение модели отделено от построения и применения плана;
3. apply связан с revision и fingerprint ранее показанного плана;
4. незарегистрированный объект не принимается под управление по одному имени;
5. потеря ownership marker запрещает изменение и удаление;
6. внешнее изменение по умолчанию создаёт конфликт;
7. удаляются только зарегистрированные объекты с повторной проверкой владельца;
8. ошибка применения восстанавливает предыдущую конфигурацию;
9. lock и revision защищают от параллельных и устаревших операций;
10. пользовательские строки не формируют shell-команды;
11. режим preview не создаёт enforcing firewall/shaper objects;
12. повторное построение одинакового состояния идемпотентно.

Наличие теста подтверждает поведение чистой логики на fixture-данных, но не выполнение операции внутри OPNsense.

### 6. Проверить интерфейс по исходникам

Без OPNsense можно проверить только статические свойства:

- основные поля имеют понятные label и help;
- служебные UUID, revision и вычисляемые состояния скрыты из форм;
- опасные действия требуют явного подтверждения;
- обычная форма короткая, редкие ограничения находятся в advanced mode;
- все строки интерфейса присутствуют в `ru_RU.po`;
- технические значения не выдаются за пользовательское объяснение.

Расположение элементов, работа JavaScript, Bootstrap-компонентов и фактический вид страницы остаются **непроверенными runtime-свойствами**.

### 7. Проверить документацию

Сопоставьте README, `docs/USAGE_RU.md`, Makefile и исходники. Документация должна:

- называть только фактически подтверждённые версии;
- различать сохранение, preview и apply;
- предупреждать о destructive API smoke-тесте;
- объяснять обычное и контролируемое удаление;
- не выдавать GitHub CI за тест реального трафика;
- перечислять ARM, HA и другие неподтверждённые режимы;
- давать команды, соответствующие существующим файлам и action names.

## Как оформить результат

Откройте форму [«Независимая GitHub-проверка»](https://github.com/Omnividente/opnsense-client-control/issues/new?template=independent-review.yml).

Для каждого замечания укажите:

- важность: блокирует / высокая / обычная / небольшая;
- точный SHA;
- permalink на строки или diff;
- ссылку на Actions run и нужный log step;
- что ожидалось и что найдено;
- почему это риск для пользователя или сопровождения;
- минимальное предлагаемое исправление;
- тип доказательства: `GitHub` или `требуется runtime-стенд`.

Допустимые итоговые решения:

- **исходники можно принять** — GitHub-проверяемая часть прошла, runtime явно не подтверждён;
- **нужны исправления** — есть воспроизводимые замечания к исходникам, тестам, workflow или документации;
- **проверка заблокирована** — точный SHA, Actions logs или нужные файлы недоступны.

Формулировка **«готово к production»** недопустима без отдельной проверки на реальном шлюзе.

## Оценка новых функций

Предложение оформляется через форму [«Оценка новой функции»](https://github.com/Omnividente/opnsense-client-control/issues/new?template=feature-evaluation.yml).

Нужно указать:

1. реальную задачу пользователя;
2. кто и как часто с ней сталкивается;
3. текущий обходной путь;
4. минимальное изменение;
5. риск для доступа, конфигурации и обновления;
6. стоимость сопровождения;
7. что можно автоматически проверить в GitHub;
8. какой runtime-тест всё равно потребуется;
9. решение: принять, уточнить, отложить или отклонить.

Приоритет получают функции, которые уменьшают ручные изменения, не создают второй источник истины, сохраняют preview-before-apply и имеют детерминированный тест. Биллинг, долговременная статистика, квоты и автоматическое обнаружение устройств требуют отдельного хранения данных и не добавляются только потому, что технически возможны.

## Условие завершения GitHub-only проверки

Проверка завершена, когда:

- проверяющий не является автором проверяемого SHA;
- workflow и его права изучены до доверия к результату;
- Actions run для точного SHA завершён и его logs просмотрены;
- каждый защитный инвариант связан с кодом и тестом либо оформлен как пробел;
- все замечания имеют GitHub-permalink и воспроизводимое объяснение;
- runtime-свойства явно перечислены как непроверенные;
- итог опубликован через GitHub Issue и не зависит от локального доступа автора.
