# Установка и работа с Client Control

## Назначение

Client Control помогает управлять доступом и скоростью клиентов из одного раздела OPNsense. Администратор работает с группами и понятными именами устройств, а плагин сам создаёт нужные псевдонимы, правила и ограничения скорости.

Плагин не заменяет DHCP, Captive Portal или систему учёта трафика. Адреса клиентов вводятся вручную либо импортируются из существующих псевдонимов.

## Совместимость

Проверенная конфигурация:

- TING `1.14.6_1`;
- OPNsense ABI `24.7`;
- FreeBSD `14.1`, ABI `1401000`;
- PHP `8.2.24`;
- `amd64`;
- пакет `os-client-control-1.1`.

Ограничения по версиям:

1. Пакет собирается средствами той системы, куда он будет установлен.
2. Пакет с ABI `24.7` не следует ставить на `25.x` или `26.x`.
3. Для другой версии нужно собрать новый пакет на отдельном тестовом шлюзе.
4. После новой сборки обязательно проверить страницу, API, применение правил, откат и реальный трафик.
5. Параметр `TARGET_VERSION` лишь разрешает скрипту работать с другой строкой версии. Он не делает исходники совместимыми автоматически.
6. Архитектуры кроме `amd64` не проверялись.
7. HA и синхронизация между несколькими узлами отдельно не проверялись.

## Что требуется для установки

На рабочем компьютере:

- POSIX shell;
- `git`, `ssh`, `scp`, `tar`;
- `sshpass`, только если используется вход по паролю;
- доступ по SSH к тестовому или целевому шлюзу.

На шлюзе:

- TING/OPNsense подходящей версии;
- FreeBSD `pkg`;
- PHP и стандартная MVC-среда OPNsense;
- достаточно прав для сборки и установки пакета.

## Установка

Из корня репозитория:

```sh
./tools/deploy.sh root@opnsense-host
```

Если доступ разрешён только по паролю, передайте его через переменную окружения `SSHPASS`. Не добавляйте пароль в командную строку, скрипты или репозиторий.

Во время установки скрипт:

1. проверяет версию и архитектуру шлюза;
2. отправляет исходники во временный закрытый каталог;
3. запускает тесты;
4. собирает один пакет;
5. проверяет пакет и его контрольную сумму;
6. сохраняет установленную версию для отката;
7. устанавливает новый пакет;
8. перезапускает `configd`;
9. запускает проверку состояния;
10. при ошибке восстанавливает прежний пакет.

После успешной установки откройте:

```text
Межсетевой экран → Клиенты
```

Прямой адрес:

```text
/ui/clientcontrol/
```

## Первый безопасный запуск

### 1. Настройки

Выберите:

- **Сети клиентов** — обычно `LAN`;
- **Интернет-интерфейсы** — обычно `WAN`;
- **Режим работы** — сначала `Только проверка`;
- **Куда применять правила** — все адреса, только интернет или адреса из выбранного псевдонима.

Нажмите **Сохранить изменения**. На этом шаге трафик ещё не меняется.

### 2. Группа

Создайте группу и задайте:

- понятное название;
- разрешение или блокировку доступа;
- режим ограничения скорости;
- скорость загрузки;
- скорость отдачи;
- единицу скорости;
- расписание, если оно уже создано в OPNsense.

Режимы скорости:

- **Без ограничения скорости** — объекты Traffic Shaper для группы не создаются;
- **Отдельно для каждого** — каждый клиент получает указанный лимит;
- **Общий на группу** — все клиенты группы делят один лимит.

Дополнительные ограничения соединений и пакетов скрыты в расширенном режиме формы. Если они не нужны, оставьте нули.

### 3. Клиент

В блоке быстрого добавления укажите:

- имя клиента;
- группу;
- тип адреса;
- один IP- или MAC-адрес.

Клиент сразу создаётся включённым. Дополнительные адреса добавляются в таблице ниже.

В карточке клиента можно задать исключение из правил группы. Эти поля скрыты в расширенном режиме, чтобы обычная форма оставалась короткой.

### 4. Проверка и применение

Откройте **Проверка и применение**.

Обычный вариант:

1. оставьте `Остановиться при внешних изменениях`;
2. нажмите **Проверить изменения**;
3. прочитайте каждую строку;
4. исправьте настройки, если результат неожиданный;
5. нажмите **Применить изменения**.

Вариант `Заменить внешние изменения этими настройками` используйте только тогда, когда точно известно, что созданные плагином объекты меняли вручную и их нужно вернуть к настройкам модуля.

После первого применения в режиме `Только проверка` переключите режим на `Применять правила`, снова проверьте список и примените его.

## Как определяется клиент

Поддерживаются:

- один точный IPv4;
- один точный IPv6;
- один MAC-адрес;
- несколько адресов у одного клиента.

Один адрес нельзя назначить двум включённым клиентам.

Для MAC-адреса OPNsense должен знать текущий IP через ARP/NDP. Пока адрес не разрешён или запись устарела, клиент считается не в сети и блокируется безопасным правилом по умолчанию.

## Импорт псевдонимов

Импорт нужен, когда устройства уже заведены в OPNsense как Host, MAC, Network или Network Group aliases.

Порядок:

1. нажмите **Найти псевдонимы**;
2. отметьте нужные записи;
3. нажмите **Проверить импорт**;
4. проверьте количество групп, клиентов и адресов;
5. исправьте показанные проблемы;
6. нажмите **Импортировать выбранные**.

Исходные псевдонимы не переименовываются, не редактируются и не удаляются.

## Текущее состояние

Вкладка показывает:

- виден ли клиент в сети;
- число открытых соединений;
- число известных адресов;
- соответствуют ли правила сохранённым настройкам;
- предупреждения по адресам и правилам.

Технические данные JSON находятся под раскрывающимся блоком и нужны в основном для поиска ошибок.

## Журнал изменений

Полная структурированная история Client Control хранится построчно в JSON в `/var/log/clientcontrol/audit.log`. В `config.xml` остаются только 200 последних записей как ограниченный резерв для интерфейса и восстановления; длинные сообщения там получают явный маркер обрезки, а в файловом журнале сохраняются полностью.

`newsyslog` ротирует журнал при достижении 2 МиБ или раз в сутки и сохраняет четыре поколения. Полную доступную историю можно получить кнопкой **Экспорт JSON** на вкладке диагностики. Файловый журнал не входит в резервную копию `config.xml`; если он нужен после переустановки системы, включите `/var/log/clientcontrol/` в отдельное резервное копирование.

## Что плагин не делает

В текущую версию не входят:

- автоматическое создание клиентов из DHCP;
- авторизация через Captive Portal, AD или RADIUS;
- денежный биллинг;
- дневные и месячные квоты по объёму;
- долговременная история трафика;
- автоматическое определение владельца устройства;
- собственное создание расписаний OPNsense;
- подтверждённая работа на ARM;
- подтверждённая работа в HA-кластере.

## Обновление

Для обновления запустите ту же команду:

```sh
./tools/deploy.sh root@opnsense-host
```

Модель клиентов и групп хранится в `config.xml` и остаётся при обновлении пакета. Скрипт сохраняет установленный пакет и автоматически возвращает его, если новая версия не проходит проверку.

## Проверка после установки или обновления

```sh
pkg check -s os-client-control
configctl clientcontrol health
configctl clientcontrol runtime_guard
configctl clientcontrol schedule
```

Ожидаемый результат:

- пакет не повреждён;
- `health` возвращает `status: ok`;
- `runtime_guard` не показывает пропущенных или лишних объектов;
- повторная проверка расписания не вносит изменений без причины.

Затем в браузере проверьте:

1. открытие всех вкладок;
2. формы группы, клиента и адреса;
3. русский текст;
4. построение списка изменений;
5. состояние клиентов.

## Независимая проверка без локального доступа

Исходники, автоматические тесты и документацию можно независимо проверить только через GitHub web UI и GitHub Actions. Локальный клон, SSH и доступ к компьютеру автора для этого не нужны. Порядок и форма отчёта описаны в [REVIEW_PLAN_RU.md](REVIEW_PLAN_RU.md).

Такая проверка не заменяет этот раздел: установку, загрузку правил, реальный трафик, ограничение скорости и откат GitHub-hosted Ubuntu runner воспроизвести не может. Эти свойства остаются непроверенными до отдельного runtime-стенда.

## API smoke-тест

Тест меняет конфигурацию и применяет правила. Запускайте его только на отдельном тестовом шлюзе.

Нужные переменные:

```sh
export CLIENT_CONTROL_API_SMOKE=apply-to-test-appliance
export CLIENT_CONTROL_URL=https://test-firewall.example
export CLIENT_CONTROL_API_KEY=...
export CLIENT_CONTROL_API_SECRET=...
export CLIENT_CONTROL_CA_FILE=/path/to/ca.pem
python3 tests/api-smoke.py
```

Для полностью изолированного одноразового стенда с самоподписанным сертификатом можно использовать `CLIENT_CONTROL_INSECURE=1`. На рабочем шлюзе так делать нельзя.

## Ручной откат пакета

Предпочтительно повторно установить известный рабочий исходный набор через `tools/deploy.sh`.

Если нужен локальный пакет отката:

1. скопируйте подходящий `dist/os-client-control-<версия>.rollback.pkg` в закрытый каталог на шлюзе;
2. проверьте его `.sha256`;
3. установите пакет;
4. перезапустите `configd`;
5. выполните проверки состояния.

Пример на шлюзе:

```sh
version=1.0
pkg add -f "/root/private-stage/os-client-control-${version}.rollback.pkg"
configctl configd restart
pkg check -s os-client-control
configctl clientcontrol health
```

## Удаление

Обычное удаление пакета сохраняет модель и созданные записи в `config.xml`, чтобы повторная установка могла продолжить работу:

```sh
pkg delete -y os-client-control
```

Это **не означает сохранение неизменной политики трафика**. После удаления runtime-hook больше не регистрирует ранние правила Client Control; на платформах с runtime registry они исчезают при следующей перезагрузке фильтра. На платформах с постоянными core-объектами они могут остаться без установленного владельца. Скрипт удаления печатает выбранный режим и это последствие до изменения пакета.

Контролируемое удаление объектов Client Control:

```sh
env DEINSTALL_CONTROLLED_OBJECTS=1 pkg delete -y os-client-control
```

Этот режим намеренно меняет политику трафика: удаляет только зарегистрированные объекты с подтверждёнными признаками принадлежности Client Control и перезагружает firewall/shaper. Клиенты и группы в модели сохраняются.
